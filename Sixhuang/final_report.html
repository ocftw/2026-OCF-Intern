1. 簡介

這是一套可重現（reproducible，任何人重跑都能得到相同結果）的評測工具，比較多個「視覺語言模型（VLM，Vision-Language Model，能同時看圖又懂文字的 AI）」在兩件事上的表現：

  1. TC_STR：辨識圖片中的繁體中文短文字，類似 OCR（Optical Character Recognition，光學文字辨識）。
  2. OminDocBench（原始拼字保留，正確應為 OmniDocBench）：把整頁文件（標題、表格、公式、多欄排版）轉成結構化 Markdown。

兩套工具都用 Ollama（在本機端跑開源大型語言模型的工具，不用連外部雲端）依序載入不同模型、餵同一批圖片並記分。核心堅持是「公平比較」：所有模型看到的圖片、提示詞（prompt）、參數完全一致，不會為表現差的模型偷偷調整。

2. 設計原則

規則 白話解釋
同題同料 同一場評測，每個模型看到的圖片、提示詞、參數都一樣
一次一張圖 每次請求（request）只送一張圖，不批次塞多張
依序換模型 測完一個才卸載、換下一個，避免顯示卡（GPU）記憶體被多模型同時占用
暖機不計分 模型剛載入時速度不穩，這段時間（warm-up）結果不算分
保留爛表現 答錯、答空白、被截斷都算模型自己的實力，不事後清理答案
原始回應永久保留 不論好壞都存起來，方便日後查證

這樣可以確保分數低是模型能力問題，而不是測試流程出錯造成的誤判。

3. 整體運算流程

不管是 TC_STR 還是 OminDocBench，實際跑起來的流程大致長這樣：

flowchart TD A[準備工作\n下載資料集/確認模型清單] --> B[Preflight 事前檢查\n確認模型版本、顯卡是否100%佔用] B -->|失敗| X[標記 BLOCKED\n不繼續往下跑] B -->|通過| C[Smoke 小規模測試\nTC_STR取20題/OminDoc取20頁] C --> D[人工檢視結果] D -->|沒問題| E[操作者手動執行\n正式全量評測] D -->|有問題| B E --> F[逐題/逐頁推論\n寫入SQLite checkpoint] F --> G[正式評分\nTC_STR自算/OminDoc用官方Docker] G --> H[產出報告\nHTML、CSV、JSON]

幾個設計重點：

  • 不會自動跑到底：小規模測試（smoke）跑完須經人工檢視確認沒問題，才由人手動啟動正式全量評測，避免無人監督下產生一堆錯誤結果。
  • 檢查點（checkpoint）：用 SQLite（輕量資料庫）逐題記錄進度，就算評測中途被中斷也能接著跑，不用從頭開始。
  • 簽章比對（signature）：資料版本、模型版本、提示詞、參數任一改變，系統就判定是「不同的一次評測」，新舊結果不會混在一起計分。

4. 系統環境

項目 內容
雲端主機 AWS EC2
作業系統 Ubuntu 26.04 LTS
顯示卡 NVIDIA L40S，約 45GB 顯示記憶體（VRAM）
模型執行工具 Ollama 0.31.1
容器化工具 Docker（跑官方評分程式，鎖定版本避免受主機環境影響）

儲存空間分兩種角色：可重建暫存區（關機會消失，但能重下載，如資料集本身）與永久保存區（存放每次評測的檢查點／checkpoint、原始回應與報告，不因關機消失）。

5. TC_STR：繁體中文短文字辨識

  • 資料來源：esun-ai/traditional-chinese-text-recogn-dataset，官方 test split 共 3,706 筆。
  • 每張圖都用 SHA-256（一種雜湊演算法，把檔案內容轉成不重複的指紋碼）記錄指紋，確保重跑用的是同一份資料。

5.1 參與比較的 8 個模型

模型 參數量 量化方式
Gemma 4 E2B 4.6B Q4_0
Gemma 4 E4B 7.5B Q4_0
Gemma 4 12B 11.9B Q4_0
Gemma 4 26B A4B 25.2B（實際啟用約 3.8B） Q4_0
Gemma 4 31B 30.7B Q4_0
GLM OCR BF16 1.1B F16
GLM-4.6V-Flash 9B 9.4B Q4_K_M
Kimi-VL-A3B-Instruct 16B（實際啟用約 3B） Q4_K_M

參數量（parameters）：模型內部可調整的數字量，概念上越多通常代表模型懂得越多，但也更耗資源。
量化（quantization）：把模型內部數字從高精度壓縮成低精度（如 Q4 約壓到 4-bit），檔案變小、更省顯示記憶體，但可能犧牲一點準確度。
A3B／A4B：代表混合專家模型（MoE，Mixture of Experts）——總參數量很大，但每次只啟用其中一小部分「專家」，實際耗費運算資源比總參數量小很多。

提示詞要求模型「只輸出圖片中看到的文字，不加任何格式、解釋或標點以外的內容」，所有模型逐字相同。主要參數：temperature（控制輸出隨機性，0 代表每次都選最可能答案）設為 0；num_predict（最多輸出幾個 token，token 可理解為模型處理文字的最小單位）為 80；逾時 180 秒。

5.2 評分指標（皆為越高越好）

指標 白話解釋
Exact Match 答案跟正確答案（ground truth，GT）一字不差才算對
Containment Match 正確答案是否完整出現在模型答案裡
ANLS 用編輯距離（Levenshtein Distance，計算把一字串改成另一字串最少要改幾個字）算相似度，太低（< 0.5）直接算 0 分
Character F1 拆成單字比對，答對多少、又多打多少，綜合算分

有個特例：GLM OCR BF16 有時回傳正常文字，卻同時標記「未完成（done=false）」且缺統計欄位。人工確認後，只有這個模型放寬規則：有回傳文字就納入計分，但註記「無法判斷是否截斷」，且效率數據不能跟其他模型比較。

6. OminDocBench：整頁文件解析

  • 使用 Hugging Face 的 opendatalab/OmniDocBench 資料集，鎖定 v1.6 版本，共 1,651 頁，涵蓋多語言、多欄排版、表格、公式、模糊掃描等情境，比短文字辨識複雜許多。
  • 正式跑完 9 個模型：Gemma 4 系列（E2B、E4B、12B、26B A4B、31B）、Qwen3-VL（4B、32B）、InternVL3.5（4B、38B）。InternVL3.5 是社群自行轉換的 GGUF（常見模型檔案格式）版本，因官方 Ollama 模型庫沒有收錄。

提示詞要求輸出「整頁 Markdown」：保留原本閱讀順序、表格轉成保留列欄與合併儲存格的 HTML table、公式用 LaTeX（常見數學排版語法）表示、不加任何額外說明。

6.1 評分方式：官方 evaluator

跟 TC_STR 自己算分不同，這裡用 OmniDocBench 官方釘死版本的評分程式，跑在 Docker 容器裡，確保評分邏輯不因主機環境不同而跑出不一樣結果。主要指標：

指標 意義 方向
Text 正規化編輯距離 純文字跟正確答案差多少 越低越好
Formula CDM 公式結構與內容是否比對正確 越高越好
Table TEDS 表格結構（樹狀結構）相似度 越高越好
Reading Order 編輯距離 閱讀順序是否跟正確答案一致 越低越好
Overall 官方綜合分數 依官方定義

另保留跟 TC_STR 相同的 4 個補充診斷指標，但特別標註「非官方排行榜指標」，避免與正式分數混淆。

實作細節（真實除錯經驗）： 用參數量較小的模型（如 Gemma 4 E2B）跑完整測試集時，約有 30% 的輸出會出現「答案不斷復讀」（模型陷入重複輸出的迴圈）的異常。這類輸出流入官方 matching 流程後，連官方內建用來處理長輸入的 chunked Hungarian algorithm（一種區塊化的配對演算法，這裡用來把預測文字區塊跟 ground truth 區塊配對）備援機制也會一起卡死、不回傳任何結果。已知解法（見官方 GitHub issue #228）是把 evaluator 的 match_workers（平行處理的工作行程數）從預設 4 調降為 1 即可避免卡死；另外，temperature 設太低也容易誘發模型復讀，適度調高有助於減少這個現象——這點與本專案最終把 OmniDocBench 的 temperature 固定在 1.0（而非像 TC_STR 那樣設為 0）的做法相符。

三個重點：

延伸觀察：

  • 推論速度跟模型架構的關係比參數量更直接：GLM OCR BF16、Kimi-VL-A3B、GLM-4.6V-Flash 9B 這三個「非 Gemma」模型的平均延遲都在 0.27～0.41 秒之間，遠快於所有 Gemma 4 模型的 1.15～1.27 秒，可能跟量化方式（F16／Q4_K_M vs Q4_0）或模型本身的推論架構有關，不是單純的參數量差異。
  • Kimi-VL-A3B-Instruct 雖然是 MoE 架構、實際啟用參數量小，異常率卻不低（453 筆截斷），EM 僅 38.5%，顯示「MoE」本身不保證穩定性，仍要看個別模型的訓練與量化品質。

7.3 結果呈現方式

README 特別強調不把「正在跑」的分數寫死在文件裡，實際數字要以每次評測輸出資料夾裡的報告為準。從程式介紹可看到，除了本節整理的官方全語料庫分數，工具本身還會另外產出：

  • 互動式比較報告（HTML）：可在網頁上依任何指標排序、篩選「表現最好／最差／隨機抽樣」的頁面，快速找出模型的弱點情境。
  • 詳細統計：成功率、API 失敗次數、重試次數、空白輸出次數、平均延遲時間（latency）等，讓使用者分辨「哪些失敗是模型能力問題、哪些是系統工程問題」。
  • 逐頁／逐題原始紀錄：模型原始回答完整保留，供之後追查或人工複核。

TC_STR 與 OmniDocBench 兩套評測目前都已取得全量正式分數（見 7.1、7.2 節），本節整理的是產出報告本身的呈現方式，跟量化結果分開描述。

8. 小結、研究限制與未來展望

這份專案的價值不在於「哪個模型比較強」的結論，而在建立一套嚴謹、可重現、公平的評測方法論：固定資料、固定提示詞、固定參數，搭配雜湊指紋、版本鎖定、檢查點機制，確保整個過程可被追蹤、驗證與重跑。這種「先把地基打穩」的做法，對需要長期比較多個 AI 模型效能的團隊很重要，能讓「模型分數差異」真正反映模型能力差異，而非測試流程本身帶來的誤差。

研究限制：

  • GLM OCR BF16 的評分需搭配例外規則解讀：這個模型因為 completion metadata 缺失，採用放寬的計分例外（見 5.2 節），它的 EM／CM 落差、截斷率跟其他 7 個模型不是完全同等條件下比較出來的，解讀跑分時要特別留意。
  • 部分模型為社群轉換版本：InternVL3.5（4B／38B）是社群自行轉換的 GGUF 量化版，並非官方原生版本，效能可能跟原始模型有落差，不完全代表該模型系列的真實上限。
  • MoE 模型的「實際啟用參數」是估算值：Gemma 4 26B A4B、Kimi-VL-A3B-Instruct 這類混合專家模型，筆記裡標注的「實際啟用約 X B」是概念性估算，並非官方精確數字。
  • 抽樣比較報告與全語料庫結果可能有落差：互動式比較報告只挑最佳／最差／隨機各 5 頁（共 15 頁）做視覺化展示，本節採用的是全語料庫 1,651 頁的官方分數，兩者用途不同，不能互相替代。
  • 跨環境重現性有其極限：即使固定 temperature=0、鎖定模型 digest 與資料版本，換了 Ollama 版本、驅動程式或硬體，仍不保證逐字元完全一致的輸出。

未來展望：

  • 針對 TC_STR 的 GLM OCR BF16 異常樣本（2,034 筆截斷）做逐題錯誤分析，釐清具體是哪類文字內容（長句、密集小字、特殊符號）容易誘發復讀。
  • 針對 OmniDocBench 表現較弱的子項（例如小模型的 table TEDS）做更細緻的錯誤分析，找出具體是哪類表格版面（跨頁、合併儲存格、多欄）造成失分。
  • 嘗試單一變量消融實驗（ablation，一次只改一個設定觀察分數變化），釐清 prompt 寫法、生成參數、後處理規則各自對分數的貢獻，而不只是看最終總分。
  • 把互動式比較報告與本節的靜態圖表整合成同一份可持續更新的 dashboard，新模型跑完就能自動併入比較，不需要每次手動整理表格。
